# Analysium

Управление проектами и задачами для продуктовых команд: доски, спринты, бэклог,
эпики, история изменений и права доступа. Интерфейс на русском языке.

Это не клон Jira — собственный продукт со своей визуальной системой,
клавиатурным управлением и архитектурой, рассчитанной на рост.

---

## Быстрый старт

Нужны **Node 20+** и **Docker** (для PostgreSQL).

```bash
npm install && npm run setup && npm run dev
```

`setup` создаёт `apps/api/.env` со сгенерированным ключом сессий, поднимает
Postgres в Docker, применяет миграции и заливает демо-данные. Существующий
`.env` не трогает. После этого:

| Что | Где |
|---|---|
| Приложение | http://localhost:5173 |
| API | http://localhost:4000/api/v1 |
| Проверка здоровья | http://localhost:4000/health |

Кнопка демо-входа показывается только в режиме разработки: в продакшен-сборку
она не попадает вместе с учётными данными.

### Windows

Работает так же. Нужны Node 20+, Git и **Docker Desktop** (он даёт Postgres);
команды те же. Переводы строк зафиксированы в `.gitattributes`: shell-скрипты и
конфигурация всегда выгружаются с LF, иначе `scripts/backup.sh` сломался бы при
запуске внутри Linux-контейнера.

### Демо-аккаунт

На странице входа есть кнопка **«Войти как Алекс (владелец)»** — она открывает
заполненное пространство: 3 проекта, ~74 задачи, эпики, спринты, комментарии
и история.

Все демо-аккаунты, пароль у всех `demo1234`:

| Роль | Почта |
|---|---|
| владелец | `alex@acme.test` |
| администратор | `maria@acme.test` |
| участник | `john@acme.test`, `priya@acme.test`, `tomas@acme.test` |
| гость | `dana@acme.test` |

Войдите гостем, чтобы увидеть, как права работают на практике: гость видит
только те проекты, куда его добавили, и не может создавать задачи.

## Что умеет

**Работа с задачами** — доска Kanban с drag & drop и WIP-лимитами, табличный
список с настраиваемыми колонками и массовыми действиями, календарь по срокам
(перетаскивание меняет срок), бэклог и спринты для Scrum, эпики и подзадачи.

**Диаграмма Ганта** — декомпозиция работы деревом (эпик → задача → подзадача),
сводные полосы считаются по детям, прогресс взвешивается по стори-поинтам.
Связи между задачами четырёх типов с проверкой циклов на сервере, критический
путь по методу CPM, вехи, базовый план для сравнения с фактом, четыре масштаба
времени. Перетаскивание меняет даты; если перенос ломает зависимость,
приложение **предлагает** сдвинуть последователей, а не делает это молча.
Запас времени у задачи виден прямо на шкале — пунктирный хвост после полосы.

**Карточка задачи** — все поля редактируются прямо в панели, без отдельных форм.
Rich-text описание с упоминаниями `@`, чек-листами и кодом, комментарии, файлы,
полная история изменений человеческим языком: «сменил(а) статус с «В работе» на
«Готово»». Скриншот вставляется в описание или комментарий через Ctrl+V.
Повторяющиеся задачи (каждый день, по будням, неделю, месяц): закрытая задача
возвращается следующей со сдвинутым сроком. «Следить за задачей» — уведомления
о чужой задаче, или отписка от своей. Прогресс чек-листа виден на карточке.

**Выгрузка** — список проекта с текущими фильтрами выгружается в таблицу для
Excel (кнопка «Выгрузить»).

**Поиск и фильтры** — `Cmd/Ctrl + K` открывает палитру: задачи, проекты, люди,
эпики и команды. Фильтры по 12 измерениям, состояние живёт в URL — любой
отфильтрованный вид можно отправить коллеге ссылкой. Виды сохраняются.

**Команда** — пространства, роли (владелец / администратор / участник / гость),
права на уровне проекта, уведомления с центром входящих и письмами на почту,
журнал аудита.

**На телефоне** — адаптивный интерфейс; сайт ставится на главный экран как
приложение («Установить приложение» в браузере, на iPhone — «На экран «Домой»»).

**Реальное время** — изменения коллег приезжают по SSE без перезагрузки.

**Интерфейс** — «типографский планшет»: бумажный фон, чернильные рамки в 2px
и сплошные тени вместо размытия, широкий дисплейный шрифт в заголовках и
моноширинный для ключей, счётчиков и дат. Одна светлая тема — направление
построено на паре «бумага и чернила», и тёмная была бы не той же темой
приглушённой, а другим дизайном. Работа с клавиатуры, скелетоны вместо
спиннеров, осмысленные пустые состояния.

### Горячие клавиши

| Клавиша | Действие |
|---|---|
| `C` | создать задачу |
| `/` | поиск |
| `Cmd/Ctrl + K` | командная палитра |
| `G` затем `P` / `M` / `I` / `H` | проекты / мои задачи / входящие / главная |
| `E` `A` `S` `P` | заголовок / исполнитель / статус / приоритет |
| `Esc` | закрыть панель или окно |
| `?` | список всех сочетаний |

## Архитектура

Монорепозиторий на npm workspaces, строгий TypeScript везде.

```
packages/contracts    типы, Zod-схемы, права, realtime-события, ранжирование
apps/api              Fastify 5 + Prisma + PostgreSQL
apps/web              React 19 + Vite + TanStack Query + Tailwind v4
e2e                   Playwright
```

`@flowdesk/contracts` — единственный источник правды. API валидирует запросы
теми же схемами, из которых клиент берёт типы, поэтому они не могут разойтись.
Матрица прав — чистая функция, которую импортируют обе стороны: сервер для
проверки, клиент для отрисовки.

### Backend

```
apps/api/src
  domain/       чистые правила: права, иерархия задач, WIP, диффы, фильтры
  modules/      по предметным областям: routes → service → Prisma
  lib/          контекст актора, ошибки, сериализация, хранилище, аудит
  realtime/     типизированная шина событий и SSE
  plugins/      аутентификация, единая обработка ошибок
```

Правила выделены в `domain/` без единого обращения к БД или HTTP — поэтому они
покрываются unit-тестами и не дублируются в компонентах.

**Решения, которые стоит знать:**

| Тема | Решение | Почему |
|---|---|---|
| Порядок карточек | дробный ранг (LexoRank-lite) | перетаскивание = один UPDATE, а не перенумерация колонки |
| Статусы | таблица на проект + `category` | колонку можно переименовать, отчёты не сломаются |
| Сессии | непрозрачный токен, SHA-256 в БД | отзываемые сессии; утечка БД не даёт повторить вход |
| CSRF | `SameSite=Lax` + проверка `Origin` | без отдельного токена и его синхронизации |
| Пароли | `scrypt` из Node | без нативных модулей, параметры в самой строке хеша |
| Rich text | ProseMirror JSON + серверная санитизация | нет HTML-строки, в которую можно внедрить скрипт |
| Ключи задач | счётчик проекта внутри транзакции | параллельные создания не дают одинаковый ключ |
| Файлы | `StorageAdapter` | локальный диск сейчас, S3 — заменой одной строки |

### Frontend

```
apps/web/src
  app/            провайдеры: запросы, сессия, realtime, тосты, хоткеи
  ui/             дизайн-система: кнопки, поля, меню, диалоги, состояния
  components/     составные части: доска, строки, фильтры, палитра
  features/       по областям: задачи, спринты, проекты, участники, виды
  routes/         страницы
  lib/            API-клиент, ключи запросов, форматирование, локализация
```

Серверное состояние живёт только в TanStack Query, Zustand держит исключительно
состояние интерфейса (что открыто, что свёрнуто). Глобального «общего» стора нет.

Производительность: списки виртуализированы, каждая колонка доски грузится
своим лимитом, пагинация курсорная, поиск с debounce, обновления оптимистичные
там, где это безопасно.

## Разработка

```bash
npm run dev          # API и веб вместе
npm run dev:api      # только API (watch)
npm run dev:web      # только фронтенд

npm run db:migrate   # создать миграцию
npm run db:seed      # перезалить демо-данные
npm run db:studio    # Prisma Studio

npm test             # unit + интеграционные (нужен Postgres)
npm run test:e2e     # Playwright
npm run typecheck    # строгая проверка типов во всех пакетах
```

### Тесты

| Уровень | Что покрыто |
|---|---|
| unit | права, ранжирование, правила задач, фильтры, санитизация |
| интеграционные | вход, задачи, комментарии, спринты — через `fastify.inject` к настоящей БД |
| e2e | регистрация → проект → задача → исполнитель → статусы → комментарий → завершение |

Интеграционные тесты работают в отдельной схеме `flowdesk_test`, которая
пересоздаётся перед запуском и удаляется после — рабочие данные не затрагиваются.

### Переменные окружения

`apps/api/.env` (пример — в `.env.example`):

```
DATABASE_URL=postgresql://flowdesk:flowdesk@localhost:5433/flowdesk?schema=public
PORT=4000
SESSION_SECRET=<минимум 24 символа>
WEB_ORIGIN=http://localhost:5173
UPLOAD_DIR=./uploads
```

Конфигурация проверяется при старте: неверные значения роняют приложение сразу,
а не на первом запросе.

## Развёртывание

Пошаговая инструкция для боевого домена — в [DEPLOY.md](DEPLOY.md). Ниже —
как всё устроено.

Продакшен собирается в три контейнера: Postgres, API и Caddy. Caddy сам
получает и продлевает сертификат Let's Encrypt, отдаёт статику и проксирует
`/api/*` в API.

**Приложение и API живут на одном origin.** Это не удобство, а условие работы:
кука сессии `SameSite=Lax`, а API отклоняет межсайтовые изменения — разнеси их
по разным хостам, и вход перестанет работать. В разработке тот же проксирующий
слой даёт Vite.

### Что нужно на сервере

Docker с Compose, открытые наружу порты 80 и 443, и A-запись домена, указывающая
на этот хост. Больше ничего: Node, Postgres и сертификаты живут внутри
контейнеров.

```bash
git clone https://github.com/BOWI1618/analysium.git && cd analysium
cp .env.production.example .env.production
# заполнить DOMAIN, ADMIN_EMAIL, POSTGRES_PASSWORD, SESSION_SECRET
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Миграции применяются при старте контейнера API через `prisma migrate deploy` —
он только проигрывает закоммиченные миграции и никогда ничего не сбрасывает,
поэтому безопасен при каждом перезапуске. Демо-данные в продакшен не заливаются:
первый аккаунт создаётся через форму регистрации и сразу получает своё
пространство.

### После первого входа

Заведите свой аккаунт, затем закройте публичную регистрацию:

```bash
# в .env.production
ALLOW_PUBLIC_REGISTRATION=false
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --no-deps api
```

Дальше команда добавляется по кодам приглашения: настройки пространства →
участники → роль → «Создать код». Человек вводит код на странице «Присоединиться»
и сам задаёт имя, почту и пароль. Код одноразовый, живёт `INVITE_TOKEN_TTL_DAYS`
дней и работает при закрытой регистрации; почта для этого не нужна. Хранится
только хеш кода, поэтому показывается он один раз — при создании.

### Обновление

```bash
git pull && docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Данные переживают пересборку: база, загруженные файлы и сертификаты лежат в
именованных томах.

### Почта: уведомления и подтверждение адреса

По умолчанию почта выключена (`MAIL_ENABLED=false`): регистрация проходит сразу,
адрес не подтверждается. Так работает локальная разработка, и это же аварийный
выход — если SMTP сломается, вход не должен зависеть от доставки писем.

С включённой почтой уведомление, не прочитанное в приложении за 10 минут, уходит
письмом (`jobs/notificationMailer.ts`). Всё, что накопилось у человека, собирается
в одно письмо, и одному человеку письма идут не чаще раза в полчаса. Выключить
письма можно в настройках аккаунта. Сервер сам не отправляет больше
`MAIL_DAILY_LIMIT` писем в сутки (по умолчанию 250) — личный ящик Яндекса
пропускает по SMTP 300, а за превышение блокирует отправку.

С `MAIL_ENABLED=true` регистрация присылает ссылку, а вход до подтверждения
отвечает `EMAIL_NOT_VERIFIED`; форма входа предлагает выслать письмо повторно.
Ссылка одноразовая и живёт `EMAIL_TOKEN_TTL_HOURS` часов, в базе хранится только
её хеш.

Это обычный SMTP, поэтому провайдер — вопрос четырёх переменных, а не кода.
Подойдёт любой: почта на своём домене (Яндекс 360, Mail.ru), бесплатный тариф
транзакционного сервиса (Brevo — 300 писем в сутки, Resend — 3000 в месяц) или
даже обычный почтовый ящик. Для команды из пяти человек хватит с запасом любого.

Включайте только после того, как настройки SMTP проверены: с включённой почтой и
недоступным сервером никто не сможет завершить регистрацию.

### Резервные копии

Контейнер `backup` снимает дамп базы раз в сутки в том `backups` и удаляет
копии старше 14 дней. Ретеншен срабатывает только после успешного дампа, так
что череда неудач не съест последнюю рабочую копию. Периодичность и срок
хранения меняются через `BACKUP_INTERVAL_SECONDS` и `BACKUP_KEEP_DAYS`.

Копия, которую ни разу не разворачивали, — не копия. Проверить:

```bash
# последний дамп
docker compose -f docker-compose.prod.yml --env-file .env.production \
  exec backup sh -c 'ls -lt /backups | head'

# развернуть его в отдельную базу и посмотреть, что данные на месте
docker compose -f docker-compose.prod.yml --env-file .env.production exec backup sh -c '
  createdb -h db -U $POSTGRES_USER restore_check &&
  pg_restore -h db -U $POSTGRES_USER -d restore_check $(ls -t /backups/*.dump | head -1) &&
  psql -h db -U $POSTGRES_USER -d restore_check -c "select count(*) from users" &&
  dropdb -h db -U $POSTGRES_USER restore_check'
```

Восстановление на место — та же команда без временной базы: остановить `api`,
`pg_restore --clean` в рабочую базу, поднять `api` обратно.

Дампы лежат в томе на том же хосте, что и база. Это спасает от испорченной
миграции или удалённых данных, но не от потери сервера — если это важно,
копируйте `/var/lib/docker/volumes/<проект>_backups` куда-нибудь наружу.

Загруженные файлы в том `uploads` дампом не покрыты: они не в базе.

### Что стоит знать

Шина событий реального времени работает внутри процесса, а состояние присутствия
хранится в памяти. Для одного инстанса это ровно то, что нужно, но со вторым
инстансом API вкладки на разных процессах перестанут видеть события друг друга —
под замену подготовлен интерфейс `EventBus`.

Логи контейнеров ограничены пятью файлами по 10 МБ на сервис: драйвер Docker по
умолчанию пишет без ограничений, и на небольшом сервере это рано или поздно
забивает диск.

## Безопасность

Права проверяются на сервере при каждом запросе — скрытая кнопка в интерфейсе
это удобство, а не защита. Запросы всегда ограничены пространством
пользователя, поэтому чужая задача возвращает 404, а не 403: существование
объекта не должно утекать. Валидация — Zod на входе каждого изменяющего
эндпоинта. Rich text хранится структурой и санитизируется на сервере. Загрузки
ограничены по размеру и типу, имена файлов не участвуют в путях. На аутентификации
отдельный жёсткий rate limit. Внутренние ошибки никогда не доходят до клиента:
пользователь видит понятный текст и `requestId`, подробности уходят в лог.

Архитектура готова к следующему слою: вебхуки и автоматизации (шина событий
уже типизирована), Telegram и push-уведомления (письма уже есть, остальные
